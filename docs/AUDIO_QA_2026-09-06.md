# Audio recovery QA — 2026-09-06

Source backups: `backups/before-audio-qa-2026-09-06/`.

## Reproduced failures and changes

The first regression run reproduced four failures in the old manager: unmute did
not restart music; changing music screens while muted lost the requested track;
pending effects could start after backgrounding; and explicitly stopping music
while backgrounded did not cancel the old track's foreground resume.

- Keep the current screen's desired music independently from active players.
  Unmute/foreground resume that track; explicit stop cancels the intent.
- Backgrounding immediately cancels all active/pending effects and players. It
  does not rely on JS fade timers completing while the app is suspended.
- Recheck foreground/mute state after asynchronous activation/loading before
  starting or retrying a player. Retry the current music after preparation failure.
- Music focus ownership prevents a late blur/unmount on an old screen from
  stopping the new screen when both screens use the same music track.
- Critical effects duck music without scheduling a competing stop. Music may
  start beneath a critical cue; low-priority effects retain their priority rules.
- Evict damaged cached players even when native pause/remove throws. Repeated
  taps use a fresh player after completion; disposal does not preload replacements.
- Initialization uses lifecycle/revision guards, preventing stale async settings
  from undoing a user's mute or registering listeners after disposal.

The installed `expo-audio/src/AudioModule.web.ts` marks `isPlaying=true` immediately
after `media.play()` and does not handle its promise rejection. The manager then
mistakes autoplay-denied music for playing music and skips recovery. Added a small
web-only HTMLAudio adapter that reads real media state, handles rejection, releases
listeners/resources, and cancels pending starts on removal. Prepared web effects
start synchronously inside gestures; user interaction can recover paused music.
Android continues to use expo-audio and its shared audio session.

No background music was added to game tables: their existing effect-only design
is unchanged. This work addresses dropped playback, not deliberate silent periods.

## Verification

- 16 audio regression cases passed, including 100 rapid effect replay/finish cycles,
  paused loop recovery, damaged native-player eviction, muted/background transitions,
  stale screen cleanup, initialization races and rejected browser autoplay.
- All 38 targeted audio + launch/localization + ranking-country tests passed.
- Client TypeScript, web export and Android Hermes export passed.
- Browser harness uses the real manager, registry, web adapter and bundled sound
  assets. Its lifecycle buttons simulate AppState transitions; browser visibility
  events are also bridged. Settings use a separate QA storage key.
- Browser playback-state observations: music loaded and playing; 100 tap requests
  completed with no active one-shot left afterward; mute produced no active players;
  unmute resumed music; background produced no active players; resume restored music;
  after boss cue completion music continued at the original volume (0.105).
- Harness: run `node scripts/build-audio-qa.cjs` in client after web export, then open
  `/audio-qa.html` on the local preview. It adds no app route or authentication bypass.
  QA artifacts are inside ignored `launch-preview` and should not be published.

## Remaining device checks

These results verify code and browser playback state, not audible output from the
owner's phone. A physical Android device was not available through adb in this task.
Before release, listen during a full match and test app switching, screen lock,
phone-call interruption, Bluetooth disconnect/reconnect, volume changes and rapid
navigation. Verify effects resume without replaying old cues, music resumes only
on music screens, and mute stays respected. The generated Android output is a
Hermes export, not an installed APK or evidence of device-level audio-focus QA.
